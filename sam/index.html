00 — Overview

Project Summary

The challenge with AI agents in operational roles is not intelligence — it is consistency. A language model without structured memory re-investigates what it already documented, forgets decisions, loses track of what changed and why, and produces different answers to the same question across sessions.

Project Sam addresses this directly. Built on the Hermes agent framework and running in a Docker container on an Ubuntu workstation, Sam is a persistent AI systems engineer with SSH access to a Raspberry Pi 4 home lab. The goal was not to deploy a chatbot for infrastructure questions — it was to design an operational agent capable of maintaining institutional knowledge, following documented procedures, and executing autonomous work on production systems.

The architecture centers on a documentation-first principle: before investigating any question, Sam consults existing documentation. A structured knowledge base — operational ledger, risk register, service inventory, configuration baselines, decision log, change history — is the primary source of truth. Live investigation is a last resort, not a first instinct.

Session continuity is solved through a snapshot system and a mandatory session start procedure. Every new session begins by loading the most recent snapshot, the tool registry, and the service inventory before accepting any work. This gives every session the same operational context regardless of how or why the previous session ended.

Managed infrastructure: Sam administers the Privacy Pi gateway — a Raspberry Pi 4 running Pi-hole, Unbound, Stubby, Tailscale, and Monit. She performs service audits, verifies configuration drift, executes maintenance tasks, and documents all operational activity in a persistent knowledge base.

02 — Implementation

Iterative Development

Sam was not deployed once and left static. Each capability was added in response to observed limitations, debugged against real behavior, and validated before moving to the next layer.

Phase 1 Container Setup & Core Identity Complete ▼

Sam runs as a named Docker container (sam-agent) on an Ubuntu workstation, using nousresearch/hermes-agent:latest. A persistent volume mounts ~/.hermes from the host to /opt/data inside the container — all operational knowledge survives restarts. The SSH key for Pi access lives at /opt/data/hermes_pi_key, and the Pi user was configured with NOPASSWD sudo to allow non-interactive remote commands.

nousresearch/hermes-agent:latest Persistent /opt/data volume SSH key for Pi access NOPASSWD sudo on Pi -w /opt/data working directory

SOUL.md structure: The initial SOUL.md draft had structural problems — the session start procedure was nested inside the Mission section, and autonomy directives floated without a header. These were corrected into dedicated sections: Identity, Mission, Session Start, Authority, Operational Reasoning, Style, Avoid. This separation matters: each section now has a clear purpose and can be updated independently.

hermes() — shell function for container management
hermes() {
  if [ "$(sudo docker ps -q -f name=sam-agent)" ]; then
    # Container running — reconnect
    sudo docker exec -it sam-agent hermes
  elif [ "$(sudo docker ps -aq -f status=exited -f name=sam-agent)" ]; then
    # Container stopped — restart
    sudo docker start -ai sam-agent
  else
    # Fresh start
    sudo docker run -it --name sam-agent \
      -w /opt/data \
      -e HERMES_HOME=/opt/data \
      --env-file ~/.hermes/.env \
      -v ~/.hermes:/opt/data \
      nousresearch/hermes-agent:latest hermes
  fi
}
Phase 2 Session Continuity System Complete ▼

Context resets are a fundamental challenge for agents in long-running operational roles. Two distinct reset types were identified and handled differently.

/new (conversation reset) clears chat context only. The container keeps running, all tools and state remain intact, and the working directory is preserved. This is the correct choice mid-session.

Container restart performs a full teardown. Any in-container state that is not on the mounted volume is lost. Required when the Docker run command itself changes (adding -w /opt/data, changing environment variables, etc.).

Session snapshots at /opt/data/snapshots/ ls -t | head -1 to find latest 4-step session start procedure /new vs container restart distinction

Both reset types lose conversational context, which the snapshot system handles. A session snapshot captures operational state at end-of-session: current tasks, recent changes, system status, decisions made. On every new session, Sam loads the most recent snapshot before accepting work — giving every session the same starting context regardless of what caused the reset.

SOUL.md — session start section
# Session Start
On every new session, before accepting work:
1. Run: ls -t /opt/data/snapshots/ | head -1 to identify the
   most recent snapshot, then read that file
2. Read /opt/data/tool_registry.md to restore awareness of
   available capabilities
3. Read /opt/data/service_inventory.md for current system state
4. Confirm readiness
Phase 3 Knowledge Architecture Complete ▼

The knowledge base was built out across multiple documents, each with a distinct purpose and clear scope. The goal was to eliminate re-investigation — if a question has been answered before, the answer should be retrievable, not rediscovered.

index.md — documentation navigation map tool_registry.md — capability catalog operations_ledger.md — append-only record risk_register.md — known risks and mitigations decisions.md — architectural decisions baselines/ — configuration drift reference

The index.md file acts as a documentation router — it answers "where should I look first?" for any operational question. The tool registry complements this by cataloging capabilities: what skills exist, what they do, and when to use them. Together, these two files are the first stop before any investigation.

The configuration baselines directory stores snapshots of critical service configurations. When a service behaves unexpectedly, Sam compares the live configuration against the baseline before touching anything — a practice that caught a real Unbound log permission error during capability testing and provided the fix path.

Documentation maintenance rules: New operational documents must be added to the index on creation. New skills must be cataloged in the tool registry. Obsolete documents are marked, not silently deleted — they may contain historical context. The index is the first file updated when anything changes.
Phase 4 Operational Reasoning Policy Complete ▼

A structured operational reasoning policy was created as a standalone file at /opt/data/operational_reasoning_policy.md. Keeping it separate from SOUL.md means it can be updated without modifying the core identity document. SOUL.md references it with a single line: Read and apply /opt/data/operational_reasoning_policy.md for all operational work.

Authority hierarchy (8 levels) Mandatory reasoning summary format Configuration drift detection requirement Context efficiency policy Knowledge preservation requirement

The policy requires a reasoning summary before any substantial task — investigation, audit, change request, or incident response. This summary must identify the request type, relevant artifacts, relevant skills, authoritative sources, and reason for selection. It serves two purposes: it forces Sam to demonstrate that appropriate documentation was consulted before acting, and it creates a reviewable record of her operational decision-making.

Operational Reasoning Summary — required format
Operational Reasoning Summary

Request Type:       Investigation (Unbound log permission error)
Relevant Artifacts: /opt/data/risk_register.md
                    /opt/data/baselines/unbound_2026-06-17.conf
                    /opt/data/service_inventory.md
Relevant Skills:    pi-connection, configuration-drift-audit
Authoritative Sources: risk_register.md (open item), live systemctl
                       and journalctl after baseline consulted
Reason For Selection: Risk register contains the documented item.
                      Baseline provides reference config. Live
                      verification confirms scope before applying fix.
Phase 5 SSH Standardization & Skill Correction Complete ▼

All Pi connections are standardized through a Pi Connection skill that uses ssh -F /opt/data/ssh_config pi "<command>". This keeps the SSH configuration in one place and abstracts connection details from operational commands.

ssh -F /opt/data/ssh_config pi Pi Connection skill as canonical method SOUL.md one-liner as enforcement override ssh-remote-management skill corrected

Sam repeatedly reverted to constructing ad-hoc SSH strings (ssh -i /opt/data/hermes_pi_key -o StrictHostKeyChecking=no pi@[IP]) despite explicit corrections. Three recurrences prompted a root-cause investigation that traced the problem to a pre-existing skill file: ssh-remote-management, written before the Pi Connection skill existed, contained the old command template throughout its examples. Because the skill was detailed and domain-specific, it consistently overrode the general directive in SOUL.md.

The correct fix was not to repeat the instruction more emphatically — it was to correct the source. The ssh-remote-management skill was updated to reference the Pi Connection skill for all connection templates, and a one-liner was added to SOUL.md as a session-level enforcement override. The combination eliminated the reversion.

Key insight: When an agent exhibits persistent non-compliance with a directive, the directive is rarely the problem. The more likely cause is a competing, more specific knowledge source overriding it. Fix the source, not the instruction.
Phase 6 Capability Validation — Five-Tier Testing Complete ▼

A five-tier testing framework was used to validate Sam's capabilities with progressively increasing complexity and autonomy. Each tier targeted a specific behavioral requirement and surfaced distinct failure modes.

Tier 1: Documentation navigation Tier 2: Live Pi investigation Tier 3: Baseline drift comparison Tier 4: Ambiguous open-ended investigation Tier 5: Autonomous work with documentation

Tier 1 (navigation and retrieval) passed without issues — Sam consulted docs before SSHing to the Pi.

Tier 2 (live investigation) revealed that Sam attempted to run pi-dns-check as a remote shell command — a command that does not exist. She had jumped to action without consulting the tool registry first. She recovered by manually checking service status, and the issue was documented in the service inventory.

Tier 3 (drift comparison) passed cleanly — Sam consulted the baseline, compared it to live Unbound configuration, and confirmed no drift.

Tier 4 (ambiguous: "something feels slow on the network, investigate") produced a solid diagnostic but was missing the mandatory operational reasoning summary before work began. Sam was asked to produce it retroactively, did so correctly, and behavior improved on subsequent tasks.

Tier 5 (autonomous work) was the most significant test. Sam was given a real open risk-register item — an Unbound log permission error found during Tier 2 testing — and told to investigate, resolve it, document the fix, and close the risk item without hand-holding. She produced the reasoning summary, connected to the Pi via the correct method, identified the permission error, applied the fix, verified the service recovered, updated the operations ledger and change history, and provided honest completion evidence. This was a real production fix on a live system, executed autonomously from start to documentation.

03 — Problem Solving

Troubleshooting Log

Failures encountered during development and the root causes behind them. Most were not reasoning failures — they were retrieval and configuration failures.

Session start reading wrong SOUL.md — wrong working directory
On first launch, Sam started in the Hermes container default working directory rather than /opt/data. She loaded the framework's default SOUL.md instead of the custom one, initializing with the wrong identity and no knowledge of the knowledge base.
→ Added -w /opt/data to the docker run command. The flag is the difference between the correct and incorrect startup — a single missing argument.
SSH string reversion — three separate corrections, same root cause
Sam repeatedly reverted to ad-hoc SSH strings despite explicit instruction to use the Pi Connection skill. Traced after the third recurrence to a pre-existing ssh-remote-management skill file containing the old command template in every example. The skill's specificity and domain match made it override the general SOUL.md directive consistently.
→ Updated ssh-remote-management skill to reference Pi Connection for all SSH operations. Added one-liner to SOUL.md as a session-level override. Both together eliminated the reversion — neither alone was sufficient.
pi-dns-check executed as remote shell command — command does not exist
During live DNS verification, Sam attempted to run pi-dns-check on the Pi as if it were a shell alias. The command does not exist. She had not consulted the tool registry or service inventory before acting, and filled the knowledge gap with a plausible guess.
→ Documented correct DNS verification procedure in service_inventory.md (systemctl status, dig queries, journalctl). Noted in the Tier 2 test findings that tool registry consultation must precede live action.
Session snapshot skill trigger phrase interpreted as programmatic invocation
When asked to take a session snapshot, Sam attempted to invoke the skill using send_message and skill_run — internal tool calls — rather than executing the defined steps directly. The skill's "Trigger phrase:" language was misread as a function signature rather than as a conversational cue.
→ Rewrote the skill invocation section: "Execute the steps below directly using available tools. Do not attempt to call this skill programmatically or via send_message." The manual fallback path she eventually used was the correct one — it just needed to be documented as the first approach.
Operational reasoning summary absent from ambiguous investigation
A Tier 4 open-ended investigation ("something feels slow on the network") began immediately without the required reasoning summary. Sam read the correct documents and ran appropriate checks, but skipped the explicit summary that the operational policy requires before investigations.
→ Retroactive summary was requested and produced correctly, demonstrating the knowledge was there. Behavior improved in subsequent investigations. The retroactive exercise reinforced the habit more effectively than a direct correction would have.

05 — Lessons Learned

What Building Sam Taught Me

These are not abstract conclusions. Each one is traceable to a specific failure, debugging session, and architectural change made in response.

Lesson 01
Agent failures are retrieval failures, not reasoning failures
When Sam attempted to run pi-dns-check as a remote command, she was not reasoning incorrectly — she was filling a retrieval gap with a plausible guess. The model's underlying reasoning was fine. The failure was that she did not have the correct information at the moment she needed it. Most agent inconsistency I observed followed this pattern: not wrong logic, but wrong or absent inputs. This reframes the engineering problem. The work is not "make the agent smarter" — it is "ensure the right information is available and consulted at the right time."
Lesson 02
Skill files compete with directives — correct at the source
The SSH reversion problem was the most instructive debugging challenge. A general directive in SOUL.md ("always connect via ssh -F ...") was repeatedly overridden by a specific, detailed skill file containing the old command template. Specificity and domain-relevance made the skill file authoritative in the agent's context, regardless of the explicit instruction. Repeating the directive louder — restating it, emphasizing it, correcting it mid-session — produced temporary compliance at best. The durable fix required updating the competing source. This has a broader implication: if an agent consistently violates an instruction, look for a more specific competing knowledge source before assuming the instruction needs to be rewritten.
Lesson 03
Context is a resource to architect, not a prompt to expand
Early session start procedures tried to preload everything: full operational docs, large inventories, baselines, change history. This consumed context that should be available for actual work, and created a situation where every task started with a bloated, redundant preamble. The redesign separated always-load (snapshot, tool registry, service inventory — small, high-value) from on-demand (full docs, baselines, change history — consulted only when relevant). The documentation index and tool registry became routers pointing to the right document rather than comprehensive sources containing all information. Treating context as a finite architectural resource — something to be managed with the same discipline as memory or disk — produced a more consistent and efficient agent than any amount of prompt expansion did.
Lesson 04
Documentation-first compounds — each session improves the next
The operational ledger, risk register, and service inventory are not just records — they are inputs to future sessions. When Sam documents a finding (the Unbound permission error), corrects a skill (the SSH template), or records a decision (connection method standardization), that information is available to every subsequent session without any re-investigation. After enough sessions, the knowledge base begins to anticipate questions before they are asked. This does not happen automatically with AI assistants — it requires deliberate architectural choices about what gets persisted and where. But once the infrastructure exists, the compounding effect is real and measurable: questions that took investigation in early sessions are answered from documentation in later ones.
Lesson 05
Test with escalating autonomy to find failure modes before they matter
The five-tier testing framework was more useful than anticipated — not because it validated what worked, but because it surfaced what did not in a controlled, low-stakes environment. Tier 2 revealed that Sam would skip the tool registry and jump to action. Tier 4 revealed that the reasoning summary requirement was not being applied to ambiguous investigations. Tier 5 revealed that the combination of correct SSH method, proper documentation, and honest reporting was now reliable enough for autonomous production work. Finding these failure modes during capability testing meant they were corrected before they could cause problems during real operations. An agent you have not deliberately stress-tested is an agent whose failure modes you do not know.
