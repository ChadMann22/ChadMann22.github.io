00 — Overview

Project Summary

With the core DNS stack and observability layer in place, a systematic review identified several meaningful gaps: Monit's port checks confirmed TCP connectivity but not actual DNS resolution. The entire alert pipeline depended on a single transport — if WAN dropped, all alerts were silently lost. There was no historical record of system metrics over time. And the backup strategy had no offsite copy.

This phase addresses all four gaps with targeted, lightweight additions that fit the existing headless, low-maintenance design philosophy.

The most significant architectural decision was dual-channel alerting — email and push notifications firing in parallel rather than in a fallback chain. Every alert now reaches the phone independently of email delivery, which means WAN outages no longer create silent monitoring blackouts.

The remote backup solution was simplified from a full OpenSSH server deployment to a single tailscale file cp command using Taildrop — zero new attack surface, zero new services running on the laptop.

DNS Resolution Check
Monit check program block runs a real dig query through all four stack layers every 10 minutes. Tests Pi-hole, Unbound, Stubby, and DNSSEC validation independently. Catches silent failures port checks cannot detect.
Dual-Channel Alerting + WAN Monitor
monit-alert.sh now fires email AND ntfy push simultaneously on every event. A separate WAN monitor script runs every 5 minutes, requires 3 consecutive failures before declaring an outage, and sends a consolidated recovery notification when connectivity restores.
Weekly CSV Metrics
One row appended to weekly-metrics.csv with every Sunday report run. Captures DNS query volume, block rate, Unbound cache performance, Fail2ban activity, disk usage, CPU temp, and uptime. Permanent historical record — excluded from log rotation.
Remote Backup via Taildrop
Manually triggered pi-backup-remote command creates a fresh snapshot and delivers it to the sysadmin laptop over the existing Tailscale mesh using Taildrop. No OpenSSH server required on the receiving end. Works from anywhere both devices have Tailscale connected.

After — parallel delivery
Monit event
→ monit-alert.sh
├→ msmtp → Gmail

└→ local pending-alerts.log

WAN monitor — false positive mitigation

A naive ping-based WAN check fires false positives when ISPs briefly rate-limit ICMP traffic without affecting TCP connections. The WAN monitor requires three consecutive 5-minute check failures — 15 minutes of sustained outage — before declaring WAN down and alerting. This threshold was arrived at through real-world testing where a 5-minute ping gap generated a false alert while household devices continued operating normally.

wan-monitor — failure threshold logic
# Increment consecutive failure counter
COUNT=1
[ -f "$CONSECUTIVE_FILE" ] && COUNT=$(( $(cat "$CONSECUTIVE_FILE") + 1 ))
echo "$COUNT" > "$CONSECUTIVE_FILE"

if [ "$COUNT" -lt 3 ]; then
    # Not yet confirmed — log but do not alert
    exit 0
fi

# 3 consecutive failures (15 min) — declare confirmed outage

Remote backup — Taildrop vs OpenSSH

The initial design called for enabling Windows OpenSSH Server on the sysadmin laptop, generating SSH keys, and setting up key-based auth. This was rejected: the laptop is not hardened and adding a listening SSH server increases attack surface unnecessarily for an occasional manual operation.

Taildrop was the correct tool — it uses the already-trusted Tailscale tunnel, requires nothing new on the receiving device, and delivers files to the standard Downloads folder via the existing Tailscale system tray. The Pi required one one-time configuration change: sudo tailscale set --operator=pi to allow the pi user to run Tailscale file operations without root elevation.

02 — Implementation

Phase-by-Phase Deployment

Phase 1 DNS Resolution Check Complete ▼

A dedicated script performs four functional DNS tests on every invocation: a real dig query through Pi-hole on port 53, direct to Unbound on port 5335, direct to Stubby on port 8053, and a DNSSEC negative test confirming that a known-bad domain is blocked rather than resolved. The script exits 0 on full pass, 1 on any failure. Monit evaluates the exit code.

4 independent resolution tests DNSSEC negative validation Every 5 Monit cycles (10 min) Logs to /var/log/privacy-pi/dns-check.log Exit code drives Monit alerting
Test domain selection matters. The test domain was initially changed from example.com to cloudflare.com which caused immediate false failures — cloudflare.com appeared on a Pi-hole blocklist. example.com is IANA-reserved specifically for testing and will never appear on any blocklist.
check-dns-resolution.sh — core logic
# Test 1: Full stack via Pi-hole
RESULT=$(dig +short +timeout=3 +tries=1 example.com @127.0.0.1 2>/dev/null)
[ -z "$RESULT" ] && FAILURES=$((FAILURES + 1))

# Test 2: Direct to Unbound
RESULT=$(dig +short +timeout=3 +tries=1 example.com @127.0.0.1 -p 5335 2>/dev/null)
[ -z "$RESULT" ] && FAILURES=$((FAILURES + 1))

# Test 3: Direct to Stubby
RESULT=$(dig +short +timeout=3 +tries=1 example.com @127.0.0.1 -p 8053 2>/dev/null)
[ -z "$RESULT" ] && FAILURES=$((FAILURES + 1))

# Test 4: DNSSEC — bad domain must NOT resolve
RESULT=$(dig +short +timeout=3 +tries=1 dnssec-failed.org @127.0.0.1 2>/dev/null)
[ -n "$RESULT" ] && FAILURES=$((FAILURES + 1))

[ "$FAILURES" -eq 0 ] && exit 0 || exit 1
monitrc — program check block
check program dns_resolution
    with path "/usr/local/bin/check-dns-resolution.sh"
    every 5 cycles
    if status != 0 then exec "/usr/local/bin/monit-alert.sh"
Phase 2 Dual-Channel Alerting + WAN Monitor Complete ▼

Two changes were made to the alerting layer. First, monit-alert.sh was updated to fire both email and ntfy push notifications in parallel on every alert. Second, a dedicated WAN monitor script was added to cron to detect and report internet outages independently of Monit.

Email + ntfy always fire together ntfy.sh hosted — no self-hosting Local pending-alerts.log as tertiary WAN monitor every 5 minutes 3 consecutive failures = confirmed outage Pending alerts flushed on WAN recovery
monit-alert.sh — parallel delivery function
deliver_alert() {
    local subject="$1"
    local body="$2"
    local ntfy_priority="${3:-default}"

    # Always write locally first
    log_local "$subject" "$body"

    # Email — fires independently
    send_email "$subject" "$body"

    # ntfy — fires independently, regardless of email result
    send_ntfy "Privacy-Pi: $subject" "$body" "$ntfy_priority"
}

The ntfy send function uses curl with a 5-second timeout to POST to the personal topic URL. ntfy.sh caches notifications server-side — if the phone is offline when the alert fires, the notification is delivered when the phone next connects. This is the key advantage for WAN-down scenarios.

Phase 3 Weekly CSV Metrics Complete ▼

A CSV append block was added to the existing weekly report script. Every Sunday at 8AM, after the email report is sent, a single row is appended to /var/log/privacy-pi/weekly-metrics.csv. The header row is written automatically on first run. The file is excluded from logrotate — it grows indefinitely as a permanent trending record.

Appended with weekly report (Sun 8AM) CSV excluded from log rotation Emailed alongside weekly report pi-csv-email alias for on-demand export
weekly-metrics.csv — column schema
date, total_queries, blocked, block_pct, forwarded, cached,
unbound_cache_hits, unbound_hit_pct,
f2b_bans_total, ssh_failures_7d,

The CSV is emailed as plain text with the weekly report and can be pasted directly into a Google Sheet — one permanent Sheet with the header row set once, then one row pasted each week as it arrives, building a chart-ready history over time.

Phase 4 Remote Backup via Taildrop Complete ▼

A manually-triggered remote backup script pushes a fresh config snapshot to the sysadmin laptop via Tailscale Taildrop. The entire implementation required two things: enabling Taildrop receive on the Windows laptop (a single checkbox, on by default) and granting the pi user Tailscale operator permissions on the Pi.

tailscale file cp — no OpenSSH needed sudo tailscale set --operator=pi Connectivity verified before transfer Works remotely from anywhere on tailnet Remote snapshot cleaned up after send
pi-backup-remote.sh — transfer step
# Verify adminlab is reachable in the tailnet
if ! sudo -u pi tailscale status 2>/dev/null | grep -q "adminlab"; then
    echo "ERROR: adminlab not found in Tailscale status."
    exit 1
fi

# Send via Taildrop — file arrives in Downloads on laptop
sudo -u pi tailscale file cp "$TARGET" "adminlab:"
The backup includes all config files, scripts, aliases, and service unit overrides — everything needed to restore a working Privacy Pi from scratch. The snapshot is deleted from the Pi after a confirmed successful transfer.
Phase 5 MOTD & Health Check Overhaul Complete ▼

Both the login MOTD and the pi-health command were fully rewritten to surface all new monitoring data alongside the existing stack information.

WAN status with outage state display DNS resolution check status from log Monit summary inline on login Last report + CSV row count pi-health: all checks with pass/fail/warn pi-health: issue count summary line

The health check now runs through nine distinct check categories — services, DNS resolution, WAN, Tailscale, Pi-hole stats, Monit summary, Fail2ban/SSH, system resources, and backup/maintenance state — and prints a total issue count at the bottom. Each check is independently color-coded with threshold-based warnings on disk, memory, and CPU temperature.

03 — Problem Solving

Troubleshooting Log

ntfy not firing — only email arriving on alerts
The initial monit-alert.sh design used ntfy as a fallback that only fired when email failed. Under normal conditions email always succeeds, so ntfy never triggered.
→ Rewrote deliver_alert() to call send_email and send_ntfy independently in sequence — both fire on every event regardless of the other's result.
WAN false positive — 5-minute outage alert during normal household usage
The monitor fired an outage alert for a window where all household devices were operating normally. ISPs can briefly rate-limit or drop ICMP ping packets without affecting TCP/UDP traffic. A single failed 5-minute ping check is insufficient evidence of a real outage.
→ Added a consecutive failure counter requiring 3 checks (15 minutes) before declaring and alerting on a confirmed outage. Counter resets on any successful ping.
Taildrop "Access denied" — file access denied error during transfer
The backup script ran as root via sudo, but tailscale file cp requires the invoking user to be an authorized Tailscale operator. Root is not automatically an operator.
→ Ran sudo tailscale set --operator=pi once to grant the pi user operator permissions. Transfer then succeeded without any script changes.
DNS resolution check false failure — cloudflare.com blocked by Pi-hole
The test domain was changed from example.com to cloudflare.com and immediately began generating false failure alerts. cloudflare.com appeared on an active Pi-hole blocklist, causing the Pi-hole port 53 test to return no answer even though the stack was fully functional.
→ Reverted to example.com — an IANA-reserved test domain that will never appear on any blocklist and is specifically designed for this type of infrastructure testing.
Permission denied clearing pending-alerts.log
The file is written by root-owned processes (WAN monitor, monit-alert.sh). Running the truncation command as the pi user without sudo was denied.
→ Updated alias to use sudo truncate -s 0 /var/log/privacy-pi/pending-alerts.log.
OpenSSH Server — rejected in favour of Taildrop
The initial remote backup design required enabling Windows OpenSSH Server on the sysadmin laptop, generating SSH keys, configuring administrators_authorized_keys, and managing file permissions. The laptop is not hardened and adding a persistent listening service was disproportionate to the use case.
→ Design replaced entirely with Tailscale Taildrop. Zero new services, zero new attack surface, simpler implementation, identical result.
