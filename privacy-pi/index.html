00 — Overview

Project Summary

This project addresses a gap common to most home networks: DNS traffic is unencrypted, unfiltered, and routed through an ISP's resolvers — exposing browsing habits and serving ads to every device on the network.

The solution is a dedicated Raspberry Pi 4 acting as a network-wide DNS gateway. Every device on the LAN — phones, TVs, laptops, smart home devices — automatically routes its DNS through the Pi without any per-device configuration.

The stack was built in phases, with each layer adding a distinct privacy or security capability: ad blocking, recursive local resolution, DNSSEC validation, DNS-over-TLS encryption, and remote access via mesh VPN.

The system is fully automated with weekly updates, config backups, and a login MOTD that surfaces live service status, network info, and quick commands on every SSH session.

The Pi runs headless on a USB SSD, connected via Ethernet to the router's LAN port. A static IP is assigned at both the OS level and via router DHCP reservation, ensuring the DNS server address never changes.
01 — Architecture

DNS Stack Design

Each component in the stack has a distinct, non-overlapping role. DNS queries flow through all four layers on every resolution.

Unbound's role shifts in Phase 3. Initially configured as a local recursive resolver, Unbound is later given a forward-zone directive pointing to Stubby. From that point forward, Unbound acts as a caching and DNSSEC validation layer — handing off actual resolution to Stubby, which encrypts it in transit.

Remote Access

Tailscale provides zero-config mesh VPN access without port forwarding. Remote devices authenticate via Tailscale and connect to the Pi's Tailscale IP, with subnet routing enabled to access the full LAN.

bash 
# Single command — advertise LAN routes, don't override local DNS stack
sudo tailscale up --advertise-routes=192.168.0.0/24 --accept-dns=false
02 — Implementation

Phase-by-Phase Deployment

The project was executed in six sequential phases. Click each phase to expand details.

Phase 0 OS Installation & System Hardening Complete ▼

Flashed Raspberry Pi OS Lite (64-bit) to a USB SSD using Raspberry Pi Imager with SSH pre-enabled. Assigned a static IP on the LAN, configured UFW to restrict inbound access to LAN-only on all ports, and installed Fail2ban for SSH brute force protection.

Static IP via dhcpcd.conf UFW — LAN-only rules Fail2ban — SSH protection
dhcpcd.conf 
# /etc/dhcpcd.conf — static IP assignment
interface eth0
static ip_address=[LAN_IP]/24
static routers=[GATEWAY_IP]
# Set to upstream DNS during install; changed to 127.0.0.1 after Unbound verified
static domain_name_servers=127.0.0.1
Phase 1 Pi-hole — Network-Wide DNS Filtering Complete ▼

Installed Pi-hole via the official script. Configured the router's DHCP server to advertise the Pi's IP as the primary DNS server for all LAN clients. This single change redirects all DNS traffic on the network through Pi-hole without touching individual devices.

One-command install Router DHCP DNS override Web dashboard on port 80 UFW — port 53 LAN-only
UFW required explicit rules for port 53 (DNS) and port 80 (dashboard). The web admin interface would not load until port 80 was opened, even on LAN — a subtle but easily missed step.
Phase 2 Unbound — Local Recursive Resolver Complete ▼

Deployed Unbound as a local recursive DNS resolver, eliminating reliance on any third-party resolver for resolution. Pi-hole was pointed at Unbound on port 5335. Root hints were downloaded and DNSSEC validation enabled using Unbound's built-in trust anchor.

Listens on 127.0.0.1:5335 DNSSEC validation QNAME minimisation Query caching
unbound.conf 
server:
    interface: 127.0.0.1
    port: 5335
    do-not-query-localhost: no   # required for Stubby forwarding
    access-control: 127.0.0.1/32 allow
    access-control: 0.0.0.0/0  refuse
    hide-identity: yes
    hide-version: yes
    qname-minimisation: yes
    harden-dnssec-stripped: yes
    prefetch: yes

forward-zone:         # added in Phase 3
    name: "."
    forward-addr: 127.0.0.1@8053
Phase 3 Stubby — DNS-over-TLS Encryption Complete ▼

Configured Stubby to listen on port 8053 and forward queries to Cloudflare and Quad9 over TLS port 853 with certificate authentication. A forward-zone was appended to Unbound's config to hand off all resolution to Stubby, completing the encrypted DNS pipeline.

TLS authentication required Cloudflare + Quad9 upstreams Port 853 encrypted egress
stubby.yml 
dns_transport_list:
  - GETDNS_TRANSPORT_TLS
tls_authentication: GETDNS_AUTHENTICATION_REQUIRED
listen_addresses:
  - 127.0.0.1@8053
upstream_recursive_servers:
  - address_data: 1.1.1.1
    tls_auth_name: "cloudflare-dns.com"
  - address_data: 9.9.9.9
    tls_auth_name: "dns.quad9.net"
Phase 4 Tailscale — Mesh VPN Remote Access Complete ▼

WireGuard was originally planned but set aside due to a Windows client compatibility issue. Tailscale was selected as a replacement — providing the same secure tunnel capability with significantly simpler setup: no key distribution, no port forwarding, and no static public IP required.

No port forwarding required Subnet routing for full LAN IPv4 + IPv6 forwarding UDP GRO optimized --accept-dns=false
Phase 5 Firewall Finalization & Maintenance Automation Complete ▼

Finalized UFW rules, corrected the default forward policy to ACCEPT (required for Tailscale subnet routing), and automated maintenance via three cron jobs and a custom MOTD script.

DEFAULT_FORWARD_POLICY=ACCEPT Weekly apt + Pi-hole updates Weekly config backups Monthly root hints refresh Login MOTD with live status

03 — Problem Solving

Troubleshooting Log

Real issues encountered during deployment and how they were diagnosed and resolved.

Unbound failed to start after adding forward-zone
Three root causes identified via unbound-checkconf: (1) do-not-query-localhost blocking loopback forwarding to Stubby, (2) auto-trust-anchor-file conflicting with a default system config file, (3) resulting corrupt root.key file.
→ Removed conflicting config file, added do-not-query-localhost: no, deleted corrupt key
Pi-hole web dashboard not loading
UFW was blocking port 80 — the firewall rules only opened ports 22 and 53 during initial setup. Confirmed via curl from the Pi itself — port 80 was responding locally but not from LAN clients.
→ Added UFW rule: allow from 192.168.0.0/24 to any port 80
Tailscale subnet routing failing silently
Tailscale reported successful connection but subnet routing did not work. IP forwarding had not been enabled (was part of the skipped WireGuard phase). Tailscale also requires explicit subnet approval in the admin console — the CLI command alone is insufficient.
→ Enabled net.ipv4.ip_forward and net.ipv6.conf.all.forwarding in sysctl; approved routes in admin console
Encrypted DNS not visible on first tcpdump check
Port 853 showed no traffic on initial capture. Unbound's cache was serving all recent queries without hitting Stubby. The check required forcing an uncached lookup to generate fresh upstream traffic.
→ Used dig against a previously unresolved domain to bypass cache; port 853 traffic confirmed immediately
