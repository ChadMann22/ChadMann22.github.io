00 — Overview

Project Summary

The Privacy Pi gateway was operational but dark — no visibility into service health, no alerting when something failed, and no consolidated reporting. If a service silently died, it would go unnoticed until the next manual login.

This phase adds a complete observability layer: automated service monitoring with self-healing restart attempts, email alerts on failure and recovery, intrusion detection with per-ban notifications, and a weekly analytics report.

The core monitoring tool chosen was Monit — a purpose-built Unix service monitor with 20+ years of production use. It was selected over a custom bash script approach because it handles state tracking, retry logic, auto-restart, and email natively.

The only custom scripting retained is the weekly report, which queries Pi-hole's SQLite database and Unbound's control socket to produce analytics that no off-the-shelf tool knows how to generate for this specific stack.

Fail2ban path

Fail2ban operates independently. On every SSH ban it fires its own email via msmtp with the offending IP and relevant log lines. Runs in parallel with Monit, not through it.

Weekly report path

A cron job fires every Sunday at 8AM. The report script queries Pi-hole's FTL database directly via SQLite, pulls Unbound cache stats via the control socket, reads Fail2ban and SSH logs, and emails a formatted plain-text summary.

Design decision — Monit over custom bash

The initial implementation plan used a hand-rolled bash monitor script with state files, checked every 5 minutes via cron. This was replaced with Monit for several reasons: Monit handles state tracking, retry logic, auto-restart attempts, and email natively — eliminating maintenance burden. It checks every 2 minutes instead of 5, uses ~15–25MB RAM with no cron overhead, and exposes a local web status dashboard at port 2812.

The one area where custom scripting was retained is alert formatting. Monit's default behavior sends one email per event, resulting in two separate emails for a single failure/recovery cycle. A custom exec script (monit-alert.sh) was written to log failure timestamps and send a single consolidated email on recovery showing down time, recovery time, and full system status.

02 — Implementation

Phase-by-Phase Deployment

Phase 1 msmtp — Email Relay Complete ▼

All alerting and reporting depends on reliable outbound email. msmtp was chosen over Postfix because it requires no daemon, no queue management, and a single config file. It sends mail and exits — nothing running in the background.

msmtp + mailutils Gmail App Password (not account password) TLS on port 587 chmod 644 for multi-user access
Gmail App Password required. Gmail does not accept account passwords for SMTP relay. A 16-character App Password must be generated at myaccount.google.com → Security → App Passwords (requires 2-Step Verification). The App Password is scoped only to mail sending and can be revoked independently.
The config file was set to chmod 644 rather than the more restrictive 600. This is required because Monit, cron jobs, and Fail2ban all run under different system users and all need to read the config to send mail. The credential stored is an App Password, not the Gmail account password, so the reduced restriction is acceptable.

tls            on
tls_trust_file /etc/ssl/certs/ca-certificates.crt
logfile        /var/log/msmtp.log

account        gmail
host           smtp.gmail.com
port           587
from           [address]@gmail.com
user           [address]@gmail.com
password       [16-char app password]

account default : gmail

Phase 4 Monit — Service Monitor & Auto-restart Complete ▼

Monit monitors all six services (pihole-FTL, unbound, stubby, tailscaled, fail2ban, and itself), performs port-level connectivity checks, and monitors disk, memory, CPU load, and the encrypted DNS upstream. On failure it attempts an automatic restart before alerting.

2-minute check interval Auto-restart on failure Port checks: 5335, 8053, 853 Disk, memory, CPU thresholds Status page at :2812 (LAN only)
Systemd unit fix required. The Debian-packaged monit.service unit file was missing Type=forking. Since Monit daemonizes itself, systemd was interpreting the initial process exit as completion and immediately marking the service dead. The unit file at /etc/systemd/system/monit.service required manual correction before the service would run persistently.
Unbound PID file not created by systemd. The initial config referenced /run/unbound.pid which Unbound does not create when running under systemd. Switched to matching "unbound" (process name match) to resolve.
monitrc — example service block
check process unbound
    matching "unbound"
    start program = "/usr/bin/systemctl start unbound"
    stop  program = "/usr/bin/systemctl stop unbound"
    if does not exist then exec "/usr/local/bin/monit-alert.sh"
    if 2 restarts within 3 cycles then exec "/usr/local/bin/monit-alert.sh"
    if failed host 127.0.0.1 port 5335 type tcp then restart
    if recovered then exec "/usr/local/bin/monit-alert.sh"

03 — Problem Solving

Troubleshooting Log

msmtp permission denied — non-zero exit status without sudo
The config file was set to 600 (root-only read). Non-root users including cron jobs and Monit could not read it, causing mail to fail silently unless run as root.
→ Changed to chmod 644. The stored credential is an App Password scoped to mail only.
Monit service exiting immediately — inactive (dead) after start
The Debian-packaged monit.service unit file was missing Type=forking. Monit daemonizes itself on startup — the parent process exits and a child continues running. Without Type=forking, systemd interpreted the parent exit as the service completing and marked it dead.
→ Created /etc/systemd/system/monit.service with Type=forking, PIDFile=/run/monit.pid, and correct ExecStart/Stop/Reload paths. Ran systemctl daemon-reload.
Monit unable to monitor Unbound — pidfile does not exist
The initial config used with pidfile "/run/unbound.pid". Unbound does not create a PID file when managed by systemd — the file path was correct for sysvinit deployments but not for systemd-managed services.
→ Changed to matching "unbound" (process name pattern match), consistent with how stubby and tailscaled are monitored.
Monit flooding terminal with /proc/attr/current errors in verbose mode
Running monit -Iv produced hundreds of "Cannot read proc file /proc/N/attr/current -- Invalid argument" lines. Monit attempts to read SELinux security attributes for all running processes, which do not exist on Raspberry Pi OS.
→ Confirmed these errors are cosmetic — they only appear in verbose mode and have no effect on daemon operation. No config change required.
Two separate emails per failure/recovery cycle
Monit's built-in alert system sends one email per state change event. A service going down then recovering produces two separate emails with no context linking them.
→ Replaced Monit's built-in email action with a custom exec script (monit-alert.sh) that logs failure timestamps to state files and sends a single consolidated recovery email showing downtime and full system status.
